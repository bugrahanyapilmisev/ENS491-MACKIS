01 Why Semantic Search?
The problem with keyword search, and how language models change everything.
Traditional search engines — and most database LIKE  queries — work by matching exact words.
This is called lexical search or keyword search. The most popular algorithm is BM25 (Best Match 25),
a refinement of TF-IDF.
Consider this example from a corpus about the film Interstellar:
The query contains the words precise and science. The best document contains scientific and
accuracy — none of the query's keywords appear verbatim . BM25 completely misses this
document. It instead returns a document that contains the word "science" literally: "Interstellar is a
2014 epic science fiction film." — which does not answer the question at all.
📌
The Key Insight
Semantic search does not match words — it matches meaning. The words "precise" and
"accuracy" are semantically close even though they are lexically different. To achieve this, we
need to represent the meaning of text as a vector in a continuous space (an embedding), where
texts with similar meanings are geometrically close to each other.
There are three major approaches using language models for search, typically combined into a
pipeline:

02 Dense Retrieval — Bi-Encoders
How text is compressed into a single vector, and how we search with it at scale.
A bi-encoder is a neural network that converts any piece of text into a dense vector (a list of floating-
point numbers). Once we have these vectors, searching becomes a matter of finding the closest
vectors to the query vector in the embedding space — a task called nearest-neighbor search.
2.1 Architecture: Inside the Bi-Encoder
The model at the heart of a bi-encoder is typically a pre-trained transformer like BERT or RoBERTa.
Here is exactly what happens, step by step:
1. Tokenization. The input text is split into subword tokens. Special tokens [CLS]  (start) and [SEP]
(end) are added automatically.
2. Embedding lookup. Each token gets an initial vector from a learned embedding table (like Word2Vec
but trainable).
3. Transformer layers. The tokens pass through multiple layers of self-attention + feed-forward
networks. After these layers, each token has a contextual vector that encodes not just the token's
identity, but also its relationship to every other token in the sequence. So the word "bank" will have
different vectors in "river bank" vs "bank account."
4. Pooling. We have one vector per token (e.g., 512 tokens × 768 dimensions). We need to collapse this
into a single vector representing the whole sentence. The most common approach is mean pooling .
5. Optional normalization. The final vector is often L2-normalized (divided by its own length) so all
vectors lie on a unit hypersphere, making cosine similarity equivalent to dot product.

The Sentence-BERT Paper (2019) — Why This Matters
Reimers & Gurevych showed that vanilla BERT with [CLS] pooling performed worse than
averaging GloVe embeddings on sentence similarity tasks. They introduced SBERT (Sentence-
BERT): fine-tune BERT with a siamese architecture and mean pooling using a contrastive loss.
This is the foundation of the sentence-transformers  library you use today.
2.3 Similarity Functions
Once we have two embedding vectors, we need a scalar similarity score. The two main options are:
cosine similarity = (u · v) / (‖u‖ × ‖v‖)   ∈ [−1, 1]
Dot product divided by the product of magnitudes. Measures the angle between vectors, not their magnitude.
Standard for semantic search.

---PAGE BREAK---
dot product = u · v = Σ uᵢ × vᵢ   ∈ (−∞, +∞)
Faster to compute. If vectors are L2-normalized first (divided by their length), dot product = cosine similarity. Use
this with FAISS for speed.

PYTHON
# Why FAISS?
# If we have 1 million documents, computing cosine similarity against ALL of
# them for every query would take seconds. FAISS uses approximate nearest-
# neighbor (ANN) algorithms (like HNSW or IVF) to answer in milliseconds.
#
# Here we normalize vectors first so that dot product = cosine similarity,
# then use IndexFlatIP (Inner Product = dot product).
# L2-normalize so all vectors have length 1
doc_emb_norm = doc_embeddings.copy()
faiss.normalize_L2(doc_emb_norm)
dim = doc_emb_norm.shape[1]      # 768
index = faiss.IndexFlatIP(dim)  # Inner Product index
index.add(doc_emb_norm)          # Add all doc vectors
print(f"Index contains {index.ntotal} vectors.")
# → Index contains 8 vectors.

2.5 Limitations of Bi-Encoders
Compression bottleneck. All meaning must be compressed into a single vector (e.g., 768 floats). For
long or complex documents, important details can be "averaged away." This is called the
representation bottleneck.
▸
No query-document interaction during encoding. The model never sees both texts simultaneously,
so it cannot model subtle interactions like negation ("NOT expensive") or comparative relationships.
▸

03 Reranking — Cross-Encoders
When accuracy matters more than speed: letting the model see both texts at once.
A cross-encoder takes a query and a document as a single combined input and produces a single
scalar relevance score. Unlike the bi-encoder, the model sees both texts simultaneously and can
model all interactions between every token of the query and every token of the document.

⚠️
Why Cross-Encoders Cannot Replace Bi-Encoders
For every query, the cross-encoder must process each candidate document separately: one
forward pass per (query, document) pair. With 1 million documents and a BERT-base model at
~20ms per pass: 1,000,000 × 20ms = 5.5 hours per query. This is completely impractical. The
solution: use a bi-encoder to shortlist 100–500 candidates in milliseconds, then apply the cross-
encoder only to that shortlist.

MULTIPLENEGATIVESRANKINGLOSS — STEP BY STEP
The loss function turns this into a classification problem over the batch: "which document is the
correct one for this query?"
STEP-BY-STEP CALCULATION (BATCH_SIZE = 4)
Step 1 — Compute similarity scores for Q1 against all 4 documents (dot product after normalization):
sim(Q1, D1) = 0.89   ← correct pair
sim(Q1, D2) = 0.31
sim(Q1, D3) = 0.24
sim(Q1, D4) = 0.19
Step 2 — Apply softmax over these 4 scores (this is exactly softmax, same as in cross-entropy
classification):
softmax score for D1 = exp(0.89) /
[exp(0.89)+exp(0.31)+exp(0.24)+exp(0.19)]
                       = 2.435 / [2.435+1.363+1.271+1.209]
                       = 2.435 / 6.278 = 0.388
Step 3 — Compute loss (cross-entropy: penalize for not giving D1 a probability of 1.0):
loss(Q1) = −log(0.388) = 0.946
After training converges, the model pushes sim(Q1,D1) much higher than the rest:
sim(Q1, D1) = 0.97   ← very high
sim(Q1, D2) = 0.08
sim(Q1, D3) = 0.05
sim(Q1, D4) = 0.03
loss(Q1) = −log(exp(0.97)/[exp(0.97)+…]) ≈ −log(0.98) ≈ 0.020   ← near
zero ✓
Total batch loss = mean of [loss(Q1) + loss(Q2) + loss(Q3) +
loss(Q4)]

---PAGE BREAK---
Backpropagation updates encoder weights to minimize this loss.
⚠️
False Negatives — The One Caveat
In-batch negatives assume that D2, D3, D4 are truly irrelevant to Q1. But what if D3 ("gross over
$677 million") happens to also partially answer Q1? This is called a false negative — a relevant
document treated as negative. It can slightly hurt training. Mitigation: deduplicate your corpus, or
use hard negative mining (run bi-encoder first, find near-miss docs, label them properly).
Bi-encoder fine-tuning with MultipleNegativesRankingLoss
PYTHON
from sentence_transformers import SentenceTransformer, InputExample, losses
from torch.utils.data import DataLoader
model = SentenceTransformer('multi-qa-mpnet-base-dot-v1')
# Only (query, positive_doc) pairs needed — no explicit negatives!
# In-batch negatives are handled automatically by the loss function.
train_examples = [
InputExample(texts=['When was Interstellar released?',
'Premiered Oct 26, 2014 in Los Angeles.']),
InputExample(texts=['Who directed the film?',
'Directed by Christopher Nolan.']),
InputExample(texts=['How much did it gross?',
'Worldwide gross over $677 million.']),
InputExample(texts=['Who starred in it?',
'Stars Matthew McConaughey and Anne Hathaway.']),
# ... add hundreds or thousands more pairs
]

#   3. Applies cross-entropy: diagonal should be high, off-diagonal low
loss_fn = losses.MultipleNegativesRankingLoss(model)
model.fit(

    epochs=3,
    warmup_steps=100,

4.2 Cross-Encoder: Dataset & Binary Cross-Entropy Loss
DATASET CONSTRUCTION
Cross-encoder training needs (query, document, relevance_label) triples. The label can be binary
(0/1) or graded (0/1/2/3). The key challenge is getting hard negatives — documents that look relevant
but aren't.
🗄️
MS MARCO — The Standard Dataset (8.8M pairs)
Microsoft collected this from Bing search logs. A user types a query → Bing returns passages →
user clicks one → that passage gets label=1 . Passages that were shown but not clicked get
label=0 . This is called implicit relevance feedback. The "not clicked" passages are often hard
negatives — they were returned by Bing because they seem related, but aren't the right answer.
Easy negatives (not useful)
POSITIVE — LABEL=1
Q: "What is the capital of Australia?"
D: "Canberra is the capital city of Australia."
EASY NEGATIVE — LABEL=0
Q: "What is the capital of Australia?"
D: "Photosynthesis converts sunlight into glucose…"
The model instantly learns to score this 0. No real learning happens. Training on only easy negatives produces a weak
model.
Hard negatives (necessary)
POSITIVE — LABEL=1
Q: "What is the capital of Australia?"
D: "Canberra is the capital city of Australia."
HARD NEGATIVE — LABEL=0

---PAGE BREAK---
Q: "What is the capital of Australia?"
D: "Sydney is the largest city in Australia and a major hub."
The model must learn the subtle distinction: "largest city" ≠ "capital." This is hard — it forces genuine learning of relevance.
HOW TO GET HARD NEGATIVES FOR YOUR OWN DATASET
1. BM25 negatives: Run BM25 on your corpus, take top-k results that are NOT relevant. These share
keywords but may not answer the question.
2. Bi-encoder negatives (best practice): Run a trained bi-encoder, take its top-k results that are NOT
relevant. These are the hardest — the bi-encoder already thinks they're relevant.
3. Random negatives: Pick random documents from the corpus. Easy, but weak.
BINARY CROSS-ENTROPY LOSS — STEP BY STEP
The cross-encoder outputs a raw logit (any real number). We apply sigmoid to get a probability, then
compute BCE loss.
p = sigmoid(raw_score) = 1 / (1 + e−score)
Squashes any real number into (0, 1). A raw score of 0 → p=0.5. Score of +3 → p=0.95. Score of −3 → p=0.047.
BCE loss = − [ y · log(p) + (1−y) · log(1−p) ]
y ∈ {0, 1} is the true label. p is the model's predicted probability. When y=1, only log(p) matters. When y=0, only
log(1−p) matters.
FOUR CONCRETE SCENARIOS
✅ CORRECT: POSITIVE PAIR, HIGH SCORE
y = 1  (relevant)
raw = +2.2

06 Chunking Long Texts
Transformer encoders have a token limit. Here is how to handle long documents correctly.
BERT-based models typically support a maximum of 512 tokens (roughly 380 words). Most real
documents — research papers, legal contracts, web pages — are much longer. We must split them
into chunks before embedding.
The choice of chunking strategy has a direct effect on retrieval quality. There are three common
approaches:
① Sentence-Level
S1: "Interstellar is a 2014 film…"
S2: "It stars Matthew McConaughey…"
S3: "Set in a dystopian future…"
✓ Fine-grained, precise matches
✗ Each sentence may lack context. "It" in S2 needs S1 to make sense.
② Paragraph / Fixed Window
Chunk 1: S1 + S2 + S3 + S4
(every 3–8 sentences)
Chunk 2: S5 + S6 + S7 + S8
✓ Good context within each chunk
✗ Information spanning the chunk boundary may be missed
③ Overlapping Chunks ★
Chunk 1: S1+S2+S3+S4
Overlap: S3+S4
Chunk 2: S3+S4+S5+S6
✓ No information is lost at boundaries
✓ Recommended for most production systems
✗ More chunks → larger index

---PAGE BREAK---
💡
Practical Rule of Thumb
Use paragraph-level chunks of 3–8 sentences with 1–2 sentence overlap, and prepend the
document title to each chunk for context: "Interstellar (Film): It stars Matthew
McConaughey…" . This gives each chunk self-contained meaning while preserving boundary
context.
07 Retrieval-Augmented Generation (RAG)
Grounding an LLM's answers in retrieved facts to reduce hallucinations.
LLMs like GPT or Llama generate fluent text but cannot reliably access specific facts. Their
knowledge is frozen at training time, and they sometimes "hallucinate" — fabricating plausible-
sounding but incorrect answers. RAG solves this by dynamically retrieving relevant documents at
inference time and injecting them into the LLM's prompt as context.
📚
Key Paper: Lewis et al., 2020
"Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" introduced RAG as a
framework: a pre-trained retriever (bi-encoder) combined with a sequence-to-sequence
generator, with gradients flowing through both. Modern RAG systems use this same idea but with
frozen retrievers and generators connected only through the prompt.

① Query Rewriting

def multi_query_rag(question: str):
# Step 1: Generate sub-queries
    subquery_prompt = f"""Break this question into 2-3 specific search queri
Output one query per line, nothing else.
Question: {question}
Queries:"""
    raw = generator(subquery_prompt, max_new_tokens=60)[0]['generated_text']
    sub_queries = [q.strip() for q in raw.strip().split('\n') if q.strip()]
print(f"Sub-queries: {sub_queries}")
# Step 2: Retrieve for each sub-query, merge results
    all_hits = {}
for sq in sub_queries:
        q_emb = bi_encoder.encode(sq, convert_to_tensor=True)

---PAGE BREAK---
        hits = util.semantic_search(q_emb, corpus_embeddings, top_k=5)[0]

③ Multi-Hop RAG
Problem: Some questions require sequential reasoning where the answer to Step 1 determines what to
ask in Step 2. You can't formulate all queries upfront.
ORIGINAL QUESTION
"Who are the top 3 car manufacturers in 2023? Do each of them make electric vehicles?"
HOP 1
Query: "largest car manufacturers 2023 by sales"
Retrieved: "Toyota: 10.5M, VW: 9.2M, Hyundai: 7.4M units in 2023"
↓ read result → now we know who the top 3 are
HOP 2
Query 2a: "Toyota electric vehicles EV lineup" → bZ4X, bZ3, Prius PHEV
Query 2b: "Volkswagen electric vehicles EV" → ID.4, ID.3, ID. Buzz
Query 2c: "Hyundai electric vehicles EV" → IONIQ 5, IONIQ 6, Kona EV
↓ all context combined → LLM generates final answer
ANSWER
"The top 3 manufacturers in 2023 were Toyota, VW, and Hyundai. All three offer EVs: Toyota
sells the bZ4X, VW offers the ID.4 and ID.3, and Hyundai has the IONIQ 5 and IONIQ 6."
⚠️
Multi-Hop requires capable models
The LLM must be able to: (1) read partial results, (2) identify what's still missing, (3)
formulate the next query autonomously. Small models (Flan-T5) struggle. Use Phi-3-
mini, Llama-3, or GPT-4 class models for reliable multi-hop behavior.

08 Evaluation Metrics
How do we know if our retrieval system is actually good? Worked examples with hand calculations.
To evaluate a search system you need three things: (1) a corpus of documents, (2) a set of test
queries, and (3) relevance judgments — human annotations saying which documents are relevant
for each query.
8.1 MAP — Mean Average Precision
MAP rewards systems that rank relevant documents higher up. It is sensitive to position: a relevant
doc at rank 1 is worth much more than one at rank 10.
Precision@k  =  (# relevant docs in top k results) / k
Fraction of the top-k results that are relevant. We compute this only at positions where a relevant document
appears.
Average Precision (AP)  =  (1 / R) × Σ   Precision@k   [only at
relevant positions k]
R = total number of relevant documents for this query. We sum Precision@k only at positions where the returned
doc is relevant, then divide by R.

MAP  =  (1 / Q) × Σ AP(q)   [averaged over all Q test queries]
The "Mean" in MAP = average of AP values over all queries. This gives a single number to compare two systems.

8.2 nDCG — Normalized Discounted Cumulative Gain
MAP treats relevance as binary (relevant / not relevant). But in reality, one document can be more
relevant than another — a perfect answer vs. a partial answer. nDCG handles graded relevance.
DCG@k  =  Σᵢ₌₁ᵏ   relevance(i) / log₂(i + 1)

---PAGE BREAK---
The denominator log₂(i+1)  is the "discount" — results at lower ranks contribute less. relevance(i) ∈ {0, 1, 2, 3}
for not relevant / partially / relevant / very relevant.
nDCG@k  =  DCG@k / IDCG@k
IDCG = Ideal DCG — the DCG you'd get if all relevant docs were ranked perfectly at the top. nDCG is always in [0, 1];
1.0 = perfect ranking.

8.3 Hit@k — Did We Find Anything Useful?
Hit@k is the simplest retrieval metric. It answers one binary question: "Is at least one relevant
document in the top-k results?" — yes (1) or no (0). No partial credit, no ranking sensitivity.
Hit@k(query)  =  1  if any relevant doc appears in top-k results,
else 0
Per-query it's binary. Averaged over all queries it becomes a fraction between 0 and 1.
Hit@k  =  (# queries where at least one relevant doc is in top-k)
/ Q

---PAGE BREAK---
Q = total number of test queries.

🎯
Why Hit@k is Critical for RAG
In a RAG pipeline, if the relevant document is not in the retrieved top-k, the LLM has no chance of
producing a correct answer — it has literally never seen the fact. Hit@k directly measures this:
"How often does our retriever give the LLM the information it needs?" A Hit@5 = 0.80 means 20%
of queries will fail regardless of how good the LLM is. Hit@k is the hard ceiling on RAG answer
accuracy.
8.4 MRR — Mean Reciprocal Rank
MRR focuses on where the first relevant document appears. Unlike MAP which scores all relevant
documents, MRR only cares about the single highest-ranked relevant result. It is particularly suited
to tasks where the user needs exactly one correct answer.
Reciprocal Rank (RR)  =  1 / rank_of_first_relevant_document
If the first relevant doc is at rank 1 → RR=1.0. At rank 2 → RR=0.5. At rank 5 → RR=0.2. If no relevant doc is found →
RR=0.
MRR  =  (1 / Q) × Σ RR(q)

---PAGE BREAK---
Q = number of queries. Average the Reciprocal Rank over all queries.

MRR vs MAP — Key Difference
MRR only looks at the first relevant result and ignores everything below. MAP looks at all relevant
results and their positions. If a query has 5 relevant documents all scattered across ranks 10–50,
MRR might still give a good score (if rank 10 hit early enough), but MAP would penalize the system
heavily for missing the other 4. Choose MRR when users need exactly one answer; MAP when
completeness matters.

8.6 RAG Evaluation — Ragas
Retrieval metrics (MAP, nDCG) only measure whether relevant documents were found. For full RAG
systems we also need to measure the quality of the generated answer. The ragas  library
automates this using an LLM-as-a-judge approach.
🎯
Faithfulness
Does the generated answer contain only information that can be found in the retrieved context? An
unfaithful answer introduces facts not present in the context — a hallucination. Score: 0–1, where 1 =
fully faithful.
❓
Answer Relevance
Does the generated answer actually address the user's question? A faithful but off-topic answer still fails.
Computed by asking an LLM to generate candidate questions from the answer, then checking if they
match the original question.
📎
Context Precision
Of the retrieved context chunks, how many were actually useful for generating the answer? Retrieval
recall is important, but retrieving irrelevant context can confuse the LLM ("lost in the middle"
phenomenon).

---PAGE BREAK---
📥
Context Recall
Were all the facts needed to answer the question actually retrieved? Computed against a ground-truth
answer: what fraction of the ground-truth claims are supported by the retrieved context?

09 Summary & Quick-Start Model Reference

Key Takeaways
Semantic search = embeddings + nearest-neighbor search. A bi-encoder encodes query and
document separately (independently) into a shared vector space, then retrieves the closest
vectors. A cross-encoder concatenates both into one sequence and produces a single relevance
score with full cross-attention — much more accurate but far too slow for first-stage retrieval.
Combine them in a two-stage pipeline. Add an LLM at the end for RAG. Evaluate with MAP, nDCG,
and Ragas.
